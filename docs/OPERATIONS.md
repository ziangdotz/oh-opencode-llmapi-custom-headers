# 运行手册

本文面向部署和维护插件的人员。当前基线：

| 项目        | 值                           |
| ----------- | ---------------------------- |
| 插件        | `0.1.0`                      |
| 配置 schema | `1`                          |
| 宿主        | OpenCode `2.4.2`             |
| 开发 Node   | `>=22`                       |
| 原生测试    | Bun `1.4.3`                  |
| 加载方式    | 宿主直接加载 TypeScript 源码 |

## 1. 发布门禁

从干净 checkout 执行：

```sh
npm ci
npm run verify:release
npm pack
```

`verify:release` 包含：

1. `format:check`：Prettier 格式。
2. `check`：TypeScript 严格类型检查。
3. `test`：22 项逻辑测试。
4. `test:tui`：Bun 原生编辑器渲染和键盘交互。
5. `check:package`：项目版本、锁文件、导出入口和发布文件白名单。

`npm pack` 通过 `prepack` 再次执行同一门禁。记录：

- 安装包文件名和 SHA-256。
- Git 提交 ID。
- OpenCode 版本。
- Node、npm、Bun 版本。
- 门禁输出和真实宿主验收结果。

CI 已提供 Windows/Linux 矩阵，但“CI 文件存在”不等于远端已执行。只有实际通过的记录才能作为交付证据。

## 2. 安装与升级运行步骤

### 安装

1. 确认 `opencode --version` 为 `2.4.2`。
2. 备份配置和数据目录。
3. 将插件目录或发布包安装到持久路径。
4. 在 `opencode.json` 和需要的 `cli.json` 中加入绝对路径。
5. 重启 OpenCode。
6. 执行 [安装](INSTALLATION.md) 第 5 节的无模型检查。

### 升级

1. 选择空闲窗口，停止相关服务；Windows 上必须退出使用插件目录的 TUI，避免 `opentui.dll` 被锁定。
2. 备份插件目录、配置、数据库和日志。
3. 替换插件或安装新包。
4. 执行 `npm ci`（源码安装）。如报 `EPERM: unlink ...opentui.dll`，确认宿主已退出后重试。
5. 重启并重复无模型检查。
6. 记录升级结果；失败时按第 4 节回滚。

宿主升级必须单独验证。不要假设插件在 2.4.2 上通过就能在更高版本运行。

## 3. 配置与数据

- 首次保存后，宿主 storage 的 `configuration` 记录优先于插件 `options`。
- 配置 schema 为 `1`，插件不会静默改写未知字段。
- 每条路由使用独立集成 `llmapi-<路由 ID>`。
- API key 由 OpenCode 保存；插件只持有集成引用。
- 旧 `displayName`、`credential` 和模型 `name` 只在加载时移除；下一次保存写回新结构。
- 路由 JSON 导出可能包含敏感请求头，备份不得上传仓库或公开工单。

## 4. 备份与恢复

### 备份

至少包含：

1. 插件目录或审核过的 `.tgz`。
2. `opencode.json`、`cli.json` 及同一配置目录中的相关文件。
3. OpenCode 数据目录；路径通过 `opencode debug paths` 确认。
4. 当前插件版本、宿主版本、提交 ID 和安装包哈希。

备份可能包含密钥和敏感请求头，必须限制访问并加密保管。不要把备份提交到 Git。

### 恢复

1. 停止宿主。
2. 恢复插件目录和匹配的配置。
3. 必要时恢复数据目录快照。
4. 重启宿主。
5. 核对菜单、路由、模型、`/connect` 和刷新。
6. 记录恢复原因和结果。

不要通过删除数据库来“修复”加载错误。先保留原始记录，再从备份恢复。

## 5. 故障恢复

| 现象                     | 处理                                                          |
| ------------------------ | ------------------------------------------------------------- |
| 保存冲突                 | 返回路由列表重新打开，读取最新 revision 后再提交              |
| 已保存但刷新或同步失败   | 配置已持久化；使用“刷新”，不要重复新增或覆盖                  |
| 新增过程中路由 ID 被占用 | 返回 ID 步骤选择其他值；已确认字段和多行草稿会保留            |
| 密钥无效                 | 在 `/connect` 检查路由独立集成和活动 API key                  |
| 配置校验失败             | 按错误信息修复字段；不要删除数据库规避错误                    |
| 编辑器崩溃               | 记录宿主版本、复现步骤和脱敏日志；保留原配置                  |
| 插件未加载               | 检查绝对路径、配置文件重复条目、宿主日志中的 `loading plugin` |
| 远程模式 RPC 不可用      | 确认服务端安装 Server 插件，两端版本一致                      |
| 模型列表为空             | 检查模型是否保存，或在允许联网时执行“发现模型”                |

## 6. 日志与可观测性

- 宿主日志目录由 `opencode debug paths` 输出。
- 插件加载日志包含 `loading plugin` 和入口路径。
- RPC 错误会以 `rpc handler failed` 记录方法名和错误信息。
- 插件没有自建日志文件、遥测或后台指标。

排查时只收集必要信息，并对以下内容脱敏：

- API key、`Authorization`、`x-api-key`。
- 内部端点、用户名、主机名。
- 数据库内容、完整配置和敏感请求头。

## 7. 支持边界

- 写入串行化和 revision 检测限于一个插件实例。
- 没有跨进程分布式锁。
- 模型发现只读一页，限制 4 MiB 和 30 秒。
- 手动刷新不访问远端目录。
- 没有后台轮询、自动重试或遥测上传。
- 端点允许本机和内网；必须由可信操作者配置。
- 没有独立安全审计、SLA、完整多协议流式验收或 WebSocket 实连验收。
- 真实模型调用和远端发现由使用者按需验收。

插件生产依赖只有 Zod；SDK、主题和 OpenTUI 是开发依赖，运行时使用宿主模块。开发依赖的本地防护和剩余告警见 [依赖审查](DEPENDENCY-REVIEW.md)。

## 8. 交付证据

每次交付建议保留：

- `npm run verify:release` 完整输出。
- `npm pack --json` 或包清单。
- 安装包 SHA-256。
- 隔离宿主无模型烟雾检查输出。
- 真实终端验收记录（如果执行）。
- 未执行项目和原因。
- 已知问题及缓解措施。

工程门禁和测试记录是交付证据，不替代外部审计、宿主安全验收或生产环境变更审批。

## 9. 变更管理

- 插件版本严格保持 `0.1.0`，除非所有者明确要求升级。
- 修复、宿主适配、依赖升级和文档更新不构成版本升级授权。
- 如果未来升级版本，必须同步 `package.json`、`package-lock.json`、包检查、文档、CHANGELOG 和安装包。
- 配置 schema 变更必须提供迁移、回滚和兼容矩阵更新。
- 公开标识变更必须提供迁移方案和真实宿主回归。

## 10. 容量与性能

插件不在请求路径上做额外网络访问；请求钩子只做内存查找、凭据解析和请求头合并。主要成本来自：

- 宿主凭据解析（每次请求）。
- 自定义请求头数量。
- 模型数量对 Provider 注册和目录缓存的影响。

没有内置配额或速率限制。大规模模型目录和大量路由应在真实宿主中评估启动和刷新耗时。
